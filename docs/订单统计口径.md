# 订单状态追踪与活跃挂单统计口径

> 说明 monitor.db 里 orders 表为什么同一个订单有多行、如何靠固定 id 追踪状态流转，
> 以及「活跃挂单」的正确统计口径。实测日期 2026-09-30。

---

## 一、订单唯一标识 vt_orderid

一个订单从本地生成到最终成交/撤单，全程用同一个唯一 id 追踪，就是 `vt_orderid`：

```
CTP.7_1770576704_14
 │  │ │           └── OrderRef   本次会话内每次下单自增的报单序号
 │  │ └────────────── SessionID  登录 CTP 时交易所分配的会话编号（可能负数，int32 溢出）
 │  └──────────────── FrontID    登录 CTP 时交易所分配的前置编号
 └─────────────────── gateway_name
```

生成机制（vnpy_ctp/gateway/ctp_gateway.py）：

1. 登录时分配前两段（onRspUserLogin，ctp_gateway.py:482-483）：
   ```python
   self.frontid = data["FrontID"]
   self.sessionid = data["SessionID"]
   ```

2. 下单时自增第三段、拼 orderid（send_order，ctp_gateway.py:820,852）：
   ```python
   self.order_ref += 1
   orderid = f"{self.frontid}_{self.sessionid}_{self.order_ref}"
   order = req.create_order_data(orderid, gateway_name)   # vt_orderid = "CTP." + orderid
   ```

3. CTP 回报时用同样的三元组重拼同一个 orderid（onRtnOrder，ctp_gateway.py:668-671）：
   ```python
   orderid = f"{data['FrontID']}_{data['SessionID']}_{data['OrderRef']}"
   ```

因为 FrontID/SessionID 是本次连接固定的，OrderRef 是本地自增后发给 CTP、CTP 原样返回的，
所以本地发单和每一次回报拼出的 orderid 完全一致 —— 这就是「一个单子固定 id」的由来。

> 会话边界：SessionID 每次登录重新分配。实测里 9-29 夜盘的单 sessionid 是负数
> （-1295181964、-899966686…），9-30 日盘是 1770576704，说明两批是两次独立登录，
> OrderRef 各自从 1 自增。

## 二、订单状态流转（生命周期）

vnpy 本地生成的 OrderData 默认状态就是 SUBMITTING（vnpy/trader/object.py:128），
datetime 默认 None（object.py:129）。之后 CTP 每次回报状态变化，on_order 都会触发一次。

一个「立即成交」的订单完整序列（实测 orders 表）：

```
id=79  SUBMITTING  traded=0  submit_time=None            本地 create_order_data 生成
id=80  SUBMITTING  traded=0  submit_time=11:22:01        CTP OnRtnOrder 回报
id=81  SUBMITTING  traded=0  submit_time=11:22:00        CTP OnRtnOrder 回报
id=82  ALLTRADED   traded=1  submit_time=11:22:00        成交回报
```

链路：策略 send_order → CTP TdApi.send_order 本地 create_order_data 推一次 SUBMITTING
（ctp_gateway.py:853）→ CTP 回报 OnRtnOrder 再推（可能多次 SUBMITTING）→ 成交推 ALLTRADED。
所以「先本地生成提交，再返回等待成交或直接成交」。

对应的成交明细在 trades 表，靠 vt_orderid 关联（挂单价 3375，成交价 3380）：

```
vt_tradeid=CTP.176312  price=3380  vol=1  time=11:22:00
```

异常单（卡在提交中没收到终态）：CTP.7_-1295181964_2 只有 2 行 SUBMITTING、traded=0，
提交时间 2026-09-29 21:01:01 至今无 ALLTRADED/撤单/拒单回报，是「僵尸单」。

## 三、订单延迟口径（2026-10 更新）

orders 表原有的 `delay_ms` 字段语义混乱（每次状态回报算「当前时刻 − 首次回报时刻」），
trades 表的 `delay_ms` 是「成交时间 − 首次回报」。本次改成两个明确口径：

- **入队延迟 `queue_delay_ms`** = 发单指令发出 → 交易所首次回报（首个非 SUBMITTING 状态）
- **撤单延迟 `cancel_delay_ms`** = 撤单指令发出 → 撤单终态（CANCELLED），仅主动撤单才有

实现（RolloverCtaEngine.py）：

1. override `send_order` / `cancel_order` 记录「指令发出时刻」到 `order_send_times` /
   `order_cancel_times`。vt_orderid 在 `super().send_order()` 内部才生成、且交易所回报
   是异步的（在 super() 返回之后才到），所以 send_time 在首次回报到来前已就位。
2. `process_order_event` 里首个非 SUBMITTING 状态算 queue_delay、首次 CANCELLED 算
   cancel_delay，缓存到 `order_queue_delay` / `order_cancel_delay`。
3. 写库时 `queue_delay_ms` / `cancel_delay_ms` 都取缓存值，所以同一订单后续状态行
   （如 ALLTRADED）仍保留入队延迟。两个 delay 字典在 `_cleanup_order_cache` 里**不清理**，
   避免成交事件先清理、订单状态行后写库时丢入队延迟（每单仅两个 float，内存可忽略）。

入队延迟终点为什么用「首个非 SUBMITTING」而非「首次 NOTTRADED」：

- 本地 `send_order` 会先推一个 SUBMITTING（`create_order_data` 本地生成），它不是交易所
  回报，不能当终点，所以排除。
- 交易所首次回报可能是直接成交（ALLTRADED）、入队排队（NOTTRADED）、部分成交
  （PARTTRADED）或拒单（REJECTED）。超价单常直接 ALLTRADED、不经过 NOTTRADED，若死等
  NOTTRADED 会永远算不出入队延迟。故以「第一个非 SUBMITTING 状态」作为入队终点最稳妥。

按最终状态：

| 最终状态 | 入队延迟 | 撤单延迟 |
|----------|----------|----------|
| ALLTRADED（直接成交，无 NOTTRADED） | 有（首次 ALLTRADED 回报算） | 0 / — |
| ALLTRADED（先入队后成交） | 有（首次 NOTTRADED 回报算） | 0 / — |
| CANCELLED（主动撤单） | 有 | 有 |
| CANCELLED（收盘被动撤） | 有 | 0 / — |
| REJECTED（发出即拒） | 有（首次 REJECTED 回报算） | 0 / — |
| SUBMITTING 卡死（僵尸单，无回报） | 0 / — | 0 / — |

> 撤单延迟只在有主动撤单指令时才有：`cancel_order` 记录 `order_cancel_times`，之后
> CANCELLED 回报到达才算。两类单没有撤单延迟：① 收盘被交易所自动撤单（没有主动指令，
> `order_cancel_times` 无该单）；② 引擎 `_mark_stale_orders()` 收盘把未成交 SUBMITTING 直接
> SQL 改成 CANCELLED 的「假撤单」，它绕过 `process_order_event`，根本不触发计算。

字段落点：orders 表 `queue_delay_ms` + `cancel_delay_ms`；trades 表的 `delay_ms` 已删除。
前端显示：StrategyDetail.vue 委托卡片、Orders.vue 活跃挂单/全部委托表格。

## 四、活跃挂单的正确定义

- **活跃挂单** = 提交中(SUBMITTING) + 未成交(NOTTRADED) + 部分成交(PARTTRADED)，
  即还没全成交、仍挂在交易所的单。
- **全部成交(ALLTRADED)** = 开仓单已变持仓 / 平仓单已完成平仓，不再是挂单。

这正是 vnpy 官方定义（vnpy/trader/object.py:14,137）：

```python
ACTIVE_STATUSES = set([Status.SUBMITTING, Status.NOTTRADED, Status.PARTTRADED])

def is_active(self) -> bool:
    return self.status in ACTIVE_STATUSES
```

所以正确口径：按 vt_orderid 取每个订单**最新一行**（id 最大），再看最新 status
是否 ∈ {SUBMITTING, NOTTRADED, PARTTRADED}。

## 五、原统计的 bug 与修复

### 原 bug

web-backend/web_backend/api.py 的 `/api/orders/stats` 与 `/api/orders/daily_freq`
都是对 orders 表**按行计数**（没按 vt_orderid 去重），把每个已全成交订单成交前的
多行 SUBMITTING 历史也算进「活跃挂单」和「委托数」。

修复前实测（2026-09-30 数据）：

| 指标 | 按行统计（原，错） | 按 vt_orderid 去重（正确） |
|------|-------------------|---------------------------|
| 活跃挂单 | 28 | 1 |
| 今日委托 | 42 | 14 |

62 行 SUBMITTING = 21 个订单 × 每单 2~3 次提交回报；按 vt_orderid 取最新状态后，
20 个 ALLTRADED（全成交）+ 1 个 SUBMITTING（僵尸单）。

### 修复

两个接口都改为：先用子查询取每个 vt_orderid 的最大 id（最新一行），再在这最新一行上
聚合统计。

- `order_stats.active`：最新状态 ∈ active 的订单数，**跨天统计**（挂单可跨夜，
  昨日报单未终态仍算当前挂单）。
- `order_stats.total` / `cancelled` / `rejected`：按今日**交易日**过滤，按唯一订单去重。
- `daily_freq.total`：当日该策略的下单数（唯一订单）；`cancelled`/`rejected` 按最新终态。

日期归口采用交易日（夜盘 20:00 后归属下一交易日，周末跳周一），规则与引擎层
position_lots.py:14 的 `trading_day()` 一致。夜盘挂的单按下一交易日归类，例如
9-29 21:01 的报单归入 9-30 交易日。

修复后实测：

```
/api/orders/stats → {'account': 'simnow', 'total': 21, 'active': 1, 'cancelled': 0, 'rejected': 0,
                     'cancel_rate': 0.0, 'by_status': {'ALLTRADED': 20, 'SUBMITTING': 1}}
/api/orders/daily_freq → 9-30 交易日共 21 单（9-29 夜盘 7 单 + 9-30 日盘 14 单），
                         与唯一订单数一致
```

## 六、代码改动清单

- `web-backend/web_backend/api.py` → `order_stats()`：按 vt_orderid 取最新状态去重统计，
  日期归口改为交易日。
- `web-backend/web_backend/api.py` → `orders_daily_freq()`：同上，去掉按行计数的 total，
  日期归口改为交易日。
- 新增 `_trading_day()` / `_current_trading_day()` 两个 helper（夜盘 20:00 后归下一交易日、
  周末跳周一），规则与引擎层 position_lots.py:14 的 `trading_day()` 一致。

顺带说明：订单页下方「活跃挂单」表格一直是对的（`/api/orders` 已用 `_latest` 去重 +
前端 filter ACTIVE_STATUS），只有顶部 stat-card 数字和底部频次表之前是错的，本次已修复。

延迟口径改动（2026-10）：
- `RolloverCtaEngine.py` → override `send_order` / `cancel_order` 记录指令发出时刻
  （`order_send_times` / `order_cancel_times`）。
- `RolloverCtaEngine.py` → `process_order_event` 首个非 SUBMITTING 状态算入队延迟、首次
  CANCELLED 算撤单延迟，缓存到 `order_queue_delay` / `order_cancel_delay`。
- `monitor/models.py`（两份）→ orders 表 `delay_ms` → `queue_delay_ms` + `cancel_delay_ms`；
  trades 表删 `delay_ms`。
- `monitor/writer.py` + `web_backend/db.py` → `_migrate()` 启动时给老 orders 表 ALTER 加新列。
- `web_backend/seed_demo.py` → 演示数据字段同步。
- 前端 StrategyDetail.vue / Orders.vue → 委托/挂单表格加「入队延迟ms」「撤单延迟ms」两列，
  成交表删「延迟ms」列。
