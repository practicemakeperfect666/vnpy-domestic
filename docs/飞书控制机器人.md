# 飞书控制机器人部署指南

通过飞书「自建应用」机器人，在群里 @机器人 远程控制策略进程（停止 / 重启）。

**实盘和模拟盘各用一个机器人**：每个账户目录一套 `app_id/secret`，各监听自己的端口（实盘 3000、模拟盘 3001）。@哪个机器人就控制哪个账户。

项目实现：`vnpy_domestic/trader/feishu_http_control.py`（HTTP 回调），跑在 `run_cta.py` 的**父进程**（常驻，非交易时段也能 @机器人）。

> 注意：本教程讲的是**自建应用机器人**（App ID / App Secret，收 @消息 + 回复）。通知用的「群机器人 webhook」（`open-apis/bot/v2/hook/xxx`）是另一套，两者独立、不混淆。

---

## 一、消息流转原理（长连接 vs Webhook）

无论哪种模式，你 @机器人 发的消息第一步都是先到飞书服务器，飞书识别是发给机器人后转发给你的程序。区别在转发方式：

| 模式 | 通道 | 公网要求 | 说明 |
|:----|:-----|:---------|:-----|
| **长连接**（WebSocket） | 程序主动连飞书，建好常驻通道 | 无需公网 IP | 消息直接走已建通道，不填地址 |
| **Webhook**（HTTP 回调） | 飞书按你填的地址主动发 HTTP 请求 | 需公网 IP 或内网穿透 | 每次消息临时发一次请求，发完即走 |

项目用的是 **Webhook（HTTP 回调）** 模式。

---

## 二、为什么一个账户要一个机器人

三个硬约束叠在一起：

1. 飞书**一个应用只能填一个**回调地址（「事件与回调 → 请求地址」）。
2. 一台机器上**一个端口只能被一个进程**持有（第二个进程 bind 会 `EADDRINUSE`）。
3. 实盘、模拟盘是两个独立的终端 / 两个 systemd unit。

所以要让两个账户都能被 @，只能各配一个应用：实盘应用回调 `:3000`，模拟盘应用回调 `:3001`，两个机器人可以拉进同一个群，@谁就是控制谁。两个账户互相独立：**停实盘不会影响模拟盘的进程、策略和持仓，反之亦然**。

> 如果坚持"一个机器人控两个账户"，就得在两个终端之间做一条指令转发通道（共享目录 / 本地 HTTP），本项目没有采用。

## 三、创建机器人（每个账户做一遍）

1. 打开[飞书开发者后台](https://open.feishu.cn/app)，「创建企业自建应用」，名称建议 `vnpy-real` / `vnpy-simnow`。
2. 应用能力 → 添加「机器人」。
3. 权限管理：开通 **接收群聊中 @机器人 消息**（`im:message.group_at_msg:readonly`）。
4. 事件与回调 → 订阅方式选「将事件发送至开发者服务器」→ 请求地址：

   | 账户 | 请求地址 |
   |:--|:--|
   | 实盘 | `http://公网IP:3000/webhook/feishu` |
   | 模拟盘 | `http://公网IP:3001/webhook/feishu` |

   记下本页的 `Encrypt Key` 与 `Verification Token`。
5. 版本管理与发布 → 创建版本 → 发布（自建应用可自己审核）。
6. 记录 `App ID`、`App Secret`（应用详情页），以及**本应用机器人**的 `open_id`。

## 四、凭证配置（各账户目录的 `.vntrader/secrets.yaml`）

```yaml
# ── 飞书控制（每个账户一套，群里的 @机器人 停止/重启）──
feishu_app_id: "cli_xxx"                  # 本账户的自建应用
feishu_app_secret: "xxx"
feishu_encrypt_key: ""                    # 没开加密留空
feishu_verification_token: "xxx"          # 必填；为空则控制不启动
feishu_bot_open_id: "ou_xxx"              # 必须是【本应用】机器人的 open_id
feishu_host: "0.0.0.0"                    # Linux 对外监听
feishu_port: 3000                         # 实盘 3000 / 模拟盘 3001（不填按账户默认）
feishu_public_url: "http://你的公网IP"    # 只用于启动时打印提示
```

要点：

- **不配 `feishu_app_id`** → 控制不启用，通知（群机器人 webhook）不受影响；
- **`feishu_verification_token` 为空** → 出于安全**不启动控制**（防止伪造回调）；
- **`feishu_bot_open_id` 必须是本应用机器人的**。填成另一个机器人的，会导致"没 @ 到本机器人"而全部忽略——日志里会打印 `mentions=[...] bot_open_id=...`，可直接对照；
- 实盘、模拟盘的 `app_id` 必须**不同**（启动日志会打印 `app_id` 前缀，一眼能看出是否配重了）。

## 五、代码位置与关键逻辑

| 文件 | 作用 |
|:--|:--|
| `vnpy_domestic/trader/feishu_http_control.py` | 回调验签（lark `event_handler`）→ `on_message` 解析 → 入队 |
| `run_cta.py` `run_parent()` | 起 uvicorn（按账户端口）、消费队列、执行 stop/restart、回复 |

`on_message` 只做解析和校验，**不直接回复**（飞书回调要求 3 秒内返回，回复由父进程主循环发）：

```python
action = "stop" if "停止" in text else "restart" if "重启" in text else ""
said = []
if "实盘" in text:
    said.append("real")
if "模拟" in text:
    said.append("simnow")

if not action:                          # 认不出动作
    ctrl_queue.put(("say", "用法：@机器人 停止 / 重启", msg_id))
elif len(said) > 1:                     # 同时写了实盘和模拟盘
    ctrl_queue.put(("say", "只写一个", msg_id))
elif said and said[0] != account:       # @ 错机器人
    ctrl_queue.put(("say", "你 @ 的是X机器人…", msg_id))
else:
    ctrl_queue.put(("do", action, msg_id))
```

主循环：

```python
kind, payload, msg_id = cmd
reply = payload if kind == "say" else apply_command(payload)
reply_text(feishu["app_id"], feishu["app_secret"], msg_id, reply)
```

`message_id` 用 `deque(maxlen=200)` 去重，防飞书重试/重复推送。

## 六、指令与行为

| 群消息 | 结果 |
|:--|:--|
| `@实盘机器人 停止` / `@实盘机器人 实盘停止` | 停实盘子进程、写 `.manual_stop`，回「停止已完成（后续时段不再自动启动，发「重启」恢复）」 |
| `@实盘机器人 重启` / `@实盘机器人 实盘重启` | 清标记、重新 spawn 子进程，回「重启已完成 (PID xxx)」；非交易时段回「重启已完成（非交易时段，子进程未启动）」 |
| `@实盘机器人 模拟盘停止` | 不执行，回「⚠️ 你 @ 的是「实盘」机器人，但指令写的是「模拟盘」」 |
| `@实盘机器人 实盘模拟盘停止` | 不执行，回「⚠️ 指令里同时出现了「实盘」和「模拟盘」，请只写一个」 |
| `@实盘机器人 停一下` | 回用法提示 |
| 不带账户词的 `@机器人 停止` | 执行（机器人身份就是账户） |

## 七、手动停止的持久化

- 「停止」时除了让子进程退出，还会写 `<账户目录>/.vntrader/.manual_stop`（内容是一行时间戳）；
- 父进程每次启动都会读这个文件：存在就**不自动启动子进程**，日志打印
  `⏸ 检测到『手动停止』标记：本终端不会自动启动子进程；@机器人 发『重启』恢复`；
- 「重启」会删除该标记；
- 所以：systemd 重启、服务器重启都不会让被停掉的账户"自己活过来"，必须显式 @机器人 重启；
- 想绕过飞书恢复，直接删文件即可：

  ```bash
  rm -f /home/ubuntu/real/.vntrader/.manual_stop
  ```

## 八、本地 Windows 测试

### 1. 安装依赖

```powershell
pip install fastapi uvicorn lark-oapi pyyaml
```

### 2. 配置 secrets.yaml

项目 `.vntrader/secrets.yaml` 填好凭证（见第四节），并设置 CTP 环境变量（本地可填假值——控制在父进程先起，不依赖 CTP 连接）：

```powershell
set CTP_USER=test
set CTP_PASSWORD=test
```

### 3. 内网穿透（两个终端要两条隧道）

```powershell
npx localtunnel --port 3000     # 实盘
npx localtunnel --port 3001     # 模拟盘
```

把拿到的公网地址分别填进两个应用的「请求地址」：`<地址>/webhook/feishu`。

### 4. 启动

```powershell
python run_cta.py
```

看到下面这行即控制已起（端口和 app_id 前缀要和自己预期一致）：

```
飞书控制已启动（实盘）app_id=cli_aaa… 监听 0.0.0.0:3000
```

> localtunnel 免费版每次重跑地址都会变、易断线，只适合本地临时测试。

## 九、Ubuntu 服务器部署

### 1. 依赖

```bash
pip3 install fastapi uvicorn lark-oapi pyyaml
```

### 2. 配置

两个账户目录各自的 `.vntrader/secrets.yaml`：`feishu_host: 0.0.0.0`、`feishu_public_url: http://你的公网IP`、`feishu_port` 分别为 3000 / 3001。

### 3. 放行端口

```bash
sudo ufw allow 3000/tcp     # 实盘
sudo ufw allow 3001/tcp     # 模拟盘
```

云服务器还要在控制台安全组里放行 TCP 3000 / 3001（两层都要）。

### 4. 启动

两个终端（或两个 systemd unit），分别在各自账户目录下：

```bash
cd /home/ubuntu/real   && python3 /home/ubuntu/vnpy-domestic/run_cta.py
cd /home/ubuntu/simnow && CTP_MODE=simnow python3 /home/ubuntu/vnpy-domestic/run_cta.py
```

### 5. 后台请求地址

| 账户 | 请求地址 |
|:--|:--|
| 实盘 | `http://公网IP:3000/webhook/feishu` |
| 模拟盘 | `http://公网IP:3001/webhook/feishu` |

## 十、验证步骤

1. **看首屏**：两个终端各打印一行 `飞书控制已启动（实盘/模拟盘）app_id=… 监听 …:3000/3001`，**两个 app_id 前缀必须不同**；
2. **@对的机器人**：`@实盘机器人 停止` → 回「停止已完成」，实盘子进程退出；再 `@实盘机器人 重启` → 回「重启已完成 (PID xxx)」；
3. **故意写错**：`@实盘机器人 模拟盘停止` → 回「你 @ 的是实盘机器人…」，且**什么都没发生**；
4. **验证持久化**：`@实盘机器人 停止` 后重启父进程（`systemctl restart`），日志应出现 `⏸ 检测到『手动停止』标记`，开盘后不会自动启动；再 `@实盘机器人 重启` 恢复。

## 十一、常见坑

| 坑 | 现象 | 解决 |
|:---|:-----|:-----|
| 两个账户用同一个应用 | 两个终端打印的 `app_id` 一样；模拟盘 3001 永远收不到消息 | 给模拟盘单独建应用，`app_id/secret/token/bot_open_id` 整组换掉 |
| 回调地址端口和 `feishu_port` 不一致 | 飞书后台校验不过 / 消息没反应 | URL 里的端口必须等于 `feishu_port`（默认实盘 3000、模拟盘 3001） |
| `Verification Token` 空 | 不启动控制（会打印提示后跳过） | 后台「事件与回调」填 `Verification Token` |
| 服务器端口没放行 | 飞书后台"请求地址校验失败" | `ufw allow` + 云厂商安全组两层都要放行 |
| `bot_open_id` 填成另一个机器人的 | 机器人收到消息但全部忽略 | `open_id` 必须是本应用机器人的；日志里 `mentions` 和 `bot_open_id` 可直接对照 |
| `on_message` 写在 register 之后 | `NameError: name 'on_message' is not defined` | 先 `def` 再 `.register_p2_im_message_receive_v1(...)` |
| reply 被 Clash 代理拦截 | 能收到消息但回复发不出，`RemoteDisconnected` | 模块顶部设 `NO_PROXY`（大小写都设） |
| localtunnel 地址变化 | 隔天 @机器人收不到消息 | 隧道重启地址就变，后台回调地址要同步改；正式环境用固定公网 IP |
| 后台还选着「长连接」 | HTTP 回调版本一直收不到消息 | 后台把订阅方式切到「将事件发送至开发者服务器」 |
| 用「3 秒窗口」过滤旧消息 | localtunnel 延迟超 3 秒，消息时灵时不灵 | 用 `message_id` 去重（`deque(maxlen=200)`） |
| 停止后过几天自己又跑起来 | 旧版本 `manual_stop` 只在内存 | 新版本已落盘 `.vntrader/.manual_stop`，检查该文件是否存在 |
